# Values and the runtime library

## Type ids

Every module starts with twelve built-in types. The types it declares are numbered from 12 on.

| Id | Type | Id | Type |
| --- | --- | --- | --- |
| 0 | `error` | 6 | `string` |
| 1 | `void` | 7 | `any` |
| 2 | `null` | 8 | `[any]` |
| 3 | `int` | 9 | `map<string, any>` |
| 4 | `float` | 10 | `[string]` |
| 5 | `bool` | 11 | `[int]` |

Runtime functions that have to understand a value take its static type id as an extra argument. For example
`to_str` takes the value and its type, so `const 3; rt to_str` formats an int and `const 11; rt to_str` formats
an `[int]` array.

## Heap objects

Heap objects start with a 16-byte header: kind (1 byte), cycle collector color, flags, element kind, type id (4 bytes),
size in bytes (4 bytes) and reference count (4 bytes). After the header:

| Kind | Layout |
| --- | --- |
| string | length at +16, UTF-8 bytes at +24 |
| array | length at +16, capacity at +24, pointer to the elements at +32 (8 bytes each, or packed, see below) |
| record | field `i` at +16 + 8·i |
| box | the boxed value at +16, with the type id of the value in the header |
| map, future | opaque, used through runtime functions |

The sized number types (`int8`, `uint8`, `int16`, `uint16`, `int32`, `uint32`, `uint64`, `float32`) are written
`int8` ... `float32` in bvm assembly. On the stack they are 64-bit words like every other value: integers are
sign- or zero-extended and `float32` values are doubles rounded to single precision. Arrays whose element type is one
of the packed types (all of them except `uint64`) store each element in 1, 2 or 4 bytes; the element kind byte in the
header says which, and `index`, `setindex` and the array runtime functions convert between the packed bytes and
64-bit words.

Values of type `any` are boxes (or the object itself when it is already on the heap). `rt box v tid` creates one
and `unbox` reads it. `rt is_type`, `rt cast` and `rt type_name` inspect it.

## Reference counting

Objects are reference counted. A new object has a count of 1, owned by whoever created it: the result of `rt`
functions, `newarr`, `new` and calls is owned by the code that receives it. `rt retain v` adds an owner and returns
`v`, `rt release v` removes one and frees the object when none is left, releasing what it holds. Both ignore `null`
and strings from the module's string pool, which are static.

Containers own their contents: `newarr` and `new` take ownership of the values they are built from, and `rt`
functions that store a value (`arr_push`, `arr_set`, `map_set`, `box`, ...) add their own owner, so the caller
still releases its copy. `index`, `getfield` and `unbox` read without adding an owner. Burn generates these
instructions itself; another language on bvm must do the same, or its objects are never freed.

Objects that only refer to each other are found by a cycle collector, which runs when enough memory has been
allocated (`BURN_GC_THRESHOLD`, 32 MB by default; `BURN_GC_STATS=1` prints a line each time) and never while spawned
threads are running. While threads run, counts are updated atomically.

## Runtime functions

`rt name` pops the function's arguments (the first argument is deepest on the stack) and pushes its result.

### Written in Burn

The runtime has two parts. The core is part of bvm and written in Rust: memory and values, reference counting,
arrays, maps, records, printing, numbers and the system (files, processes, network, time, tasks). Everything that
can be written on top of the core is written in Burn, in `lib/runtime/`:

```burn
@Runtime("str_split")
pub fun textSplit(text: string, separator: string): [string] {
    ...
}
```

`@Runtime("name")` marks the function that replaces the runtime function `name`; it takes the same arguments and
returns the same result. The module is compiled to `bvm/runtime.bvm`, which bvm embeds. When bvm loads a module
built by Burn (one marked `@RefCounted`) that uses one of those functions, it links `runtime.bvm` in and turns each
`rt name` into a call of the Burn function. Modules from other languages keep using the core directly.

The functions written in Burn may only use the core, never another function written in Burn through `rt`, and
the test suite checks that `bvm/runtime.bvm` matches `lib/runtime/`. After changing it, run from the repository
root:

```sh
burn dump --bvm lib/runtime/runtime.bn > bvm/runtime.bvm
```

A function written in Burn raises a runtime error with the built-in `__fail(message, loc)`, which is the core
function `fail`; the error points at `loc`, the place in the program that called the runtime function.

Written in Burn so far: `str_contains`, `str_replace`, `str_split`, `str_starts`, `str_ends`, `str_repeat`,
`str_trim`, `is_int_str`, `parse_int`, `is_int_radix`, `parse_int_radix`, `int_to_str_radix`, `json_parse`,
`imin`, `imax`, `iabs` and `ipow`.
